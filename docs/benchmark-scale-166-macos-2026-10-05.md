# #166 macOS CPU 벤치마크 준비와 408만 행 실측

2026-10-05, Apple M5 / RAM 16GiB에서 확인했다. **생성·측정 스크립트를 수정하고 4,089,216행까지 실측했다. 200,371,584행 실측은 하지 않았으므로 #166은 미완료다.**

2026-10-06의 후속 수정·Windows 검증은 [Windows CPU 기록](benchmark-scale-166-windows-2026-10-06.md)에 정리한다. 아래 내용은 2026-10-05 당시의 측정과 한계를 보존한 기록이다.

## 실측 결과

각 입력·엔진별 워밍업 1회 후 3회를 측정한 중앙값이다. 시간은 내부 파이프라인 실행시간이며 프로세스 시작 시간은 제외한다. 메모리는 실행별 프로세스 트리 RSS를 약 3ms 주기로 관측한 최댓값의 중앙값이다. OS가 기록한 정확한 최대 RSS나 메모리 사용량 상한은 아니다.

| 입력 행 수 | 엔진 / 요청 모드 | 시간(ms) | 관측 RSS(MiB) |
| ---: | --- | ---: | ---: |
| 227,760 | pandas | 50.5 | 145.9 |
| 227,760 | Xazz, streaming=1 요청 | 15.0 | 72.4 |
| 227,760 | Xazz, streaming=0 요청 | 16.0 | 73.1 |
| 911,662 | pandas | 194.7 | 338.0 |
| 911,662 | Xazz, streaming=1 요청 | 43.8 | 190.0 |
| 911,662 | Xazz, streaming=0 요청 | 44.6 | 196.4 |
| 4,089,216 | pandas | 881.7 | 1,242.0 |
| 4,089,216 | Xazz, streaming=1 요청 | 377.0 | 561.4 |
| 4,089,216 | Xazz, streaming=0 요청 | 403.4 | 697.8 |

원시 3회 수치, 입력·실행 파일·측정 코드 해시, 환경 정보는 [결과 JSON](../benches/results/macos-cpu-2026-10-05.json)에 보관한다. 기존 README 수치와 기준선 파일은 교체하지 않았다. 플랫폼과 pandas 입력 검사가 달라 기존 수치와 직접 비교할 수 없다.

**실제 스트리밍 엔진 사용 여부는 확정하지 못했다.** 현재 `xazz-exec/src/runtime.rs`의 `collect_lazy`는 streaming 수집 실패 시 오류를 버리고 일반 메모리 방식으로 재시도한다. 작은 검증 입력에서는 on의 `polars-stream` 진단과 off의 진단 부재를 확인했지만, 위 전체 실측에 대한 fallback 부재를 증명하지 않는다. JSON의 `streaming_actual_engine_verified`도 `false`다.

## 바꾼 동작과 입력 계약

- `--xlarge`의 누락된 원본 선택을 수정했다. large 원본 4,089,216행을 49회 반복하면 정확히 200,371,584행이다.
- 실제 원본은 최대 100,000행씩 정규화한 임시 조각을 만들고 반복 복사한다. 49배 DataFrame 결합을 제거했다. 이번 small/medium/large 생성의 관측 RSS는 165.2MiB였다. 합성 데이터는 기존 난수 순서를 유지하려고 전체 DataFrame을 먼저 만들므로 `--rows`가 메모리 제한 옵션은 아니다.
- 열 순서를 `date,station,pm10,pm25`로 고정한다. 이전 set 순서로 열이 바뀌면 Xazz의 위치 기반 스키마 연결에서 잘못된 결과가 성공처럼 반환될 수 있었다.
- 원본의 허용 숫자 결측 토큰은 코드에 명시하고, 토큰별 변환 횟수를 생성 로그에 출력한다. 실제 원본 8개에는 빈칸만 있었으며 pm10 104,162개, pm25 85,208개였다. 정규화된 측정 CSV에서는 숫자 빈칸만 결측값으로 인정한다.
- 잘못된 숫자, 무한대, 잘못된 열 순서·행 폭, LFS 포인터, 필수 문자열의 빈값을 거부한다. 문자열 `NA`·`NULL`은 보존한다. Xazz가 null로 읽는 `-`, `점검중`, `N/A`와 공백뿐인 날짜·측정소는 거부한다.
- pandas의 모든 경고 무시와 숫자 강제 변환을 제거했다. 인코딩·한국어 열 이름을 바꿔 읽는 호환 경로는 stderr에 변환 사실을 남긴다.
- 요청한 데이터가 없거나 내부 타이밍이 없으면 실패한다. 타이밍을 wall-clock으로 대체하지 않는다. 종료 코드가 0이어도 `[xazz RUNTIME ERROR]`가 있으면 실패한다.
- stdout/stderr를 파일에 기록해 출력량에 따른 파이프 교착을 막았다. 시간·RSS 초과 시 같은 프로세스 그룹과 관측한 자식을 정리한다. 관측 전에 완전히 분리된 임의의 자식까지 추적하는 OS 격리 기능은 아니다.
- 모든 측정이 성공했을 때만 결과 JSON을 교체한다. 실패 기록과 원시 로그는 별도 디렉터리에 남긴다. 데이터 생성도 파일별 원자 교체이며 여러 스케일 전체에 대한 저장 트랜잭션은 아니다.
- 기본 `--quick` 결과 구조와 소수 첫째 자리 중앙값은 기존 회귀 검사와 호환된다. `--streaming both` 결과는 모드별 별도 키를 사용하며 기본 회귀 검사 입력으로 사용하지 않는다.

## 다른 기준으로 검증한 내용

1. Python 3.9.6 / pandas 2.3.3 / NumPy 2.0.2와 Python 3.12.14 / pandas 2.2.3 / NumPy 2.3.5에서 각각 **48개 테스트**가 통과했다. psutil은 7.2.2였다.
2. 작은 CSV로 49회 반복, 3개 hash seed, 실패 시 기존 파일 보존, 타이밍 누락·중복·비정상 값, 큰 stdout/stderr, 시간·메모리 초과와 자식 정리를 검사했다. 독립 교차 검토에서 자식 정리 결함을 재현·수정했다.
3. Python 표준 계수·합계로 만든 정답과 pandas 네 단계 및 실제 release 실행 파일을 대조했다. 경계값·결측값 12행과 `NA`/`NULL` 문자열 입력에 대해 P2/P3/P4/P7 × on/off × 두 입력, **16개 실행**이 일치했다. 동점의 정렬 순서는 비교에서 제외하고 수치는 허용 오차 1e-12로 확인했다.
4. 실제 세 입력도 Python 표준 CSV 읽기로 전체를 다시 계산했다. 워밍업을 포함한 **36회 실행**의 네 단계 행 수와 Xazz의 최종 P7 집계가 일치했다. 계수를 일부러 1 바꾼 결과는 검증에 실패했다. 이 검사는 대용량 P3·P4의 모든 셀을 대조했다는 뜻은 아니다.
5. 기본 합성 227,760행은 이전 생성기 출력과 CSV 바이트가 동일했다. 새 pandas 네 단계 결과도 이전 결과와 일치했다. 기본 합성 데이터의 실제 auto 측정 결과를 기존 #147 회귀 검사에 넣어 통과했다. 이 맥의 회귀 비율 통과가 다른 CI 환경의 결과를 보장하지는 않는다.
6. 저장된 공개 v0.3.1 실행 파일에는 내부 타이밍 마커가 없어 새 측정기가 종료 코드 1로 거부했다. 성공 JSON도 만들지 않았다. 실측은 현재 소스를 새로 최적화 빌드한 실행 파일로 수행했다.
7. `cargo fmt --all -- --check`, `git diff --check`와 release 빌드가 통과했다. 이번 변경은 Python·테스트·문서이며 로컬 Rust 전체 테스트와 Clippy는 이번 브랜치에서 재실행하지 않았다. PR의 Rust CI 결과는 별도로 확인해야 한다.

실제 데이터의 P2 행 수는 small 151,346, medium 619,170, large 2,983,785였다. P3는 각 26행, P4는 10행, P7은 5행이다. 실측 stdout/stderr에 경고·오류 행이 없는 것도 확인했다.

## 환경과 재현 절차

Rust 실행 파일의 소스 기준은 `7f8e987c0e7097ba942c8d8ade2bb9b614bd4fcb`다. 버전 문자열은 `xazz 0.3.1`이지만 공개 v0.3.1 바이너리와 다르므로 JSON의 실행 파일 SHA-256으로 구분한다. 측정 Python 코드는 이 변경에 포함된 수정본이며 별도 해시를 기록했다.

macOS 26.6.2 / arm64, Apple M5 10코어, RAM 16GiB, Rust 1.99.0, macOS SDK 26.5, release 기본 최적화 설정(LTO, codegen-units=1), CPU 기본 기능으로 빌드했다. 빌드 병렬도는 2였다. GPU 기능은 사용하지 않았다. 실행당 120초·프로세스 트리 RSS 2,048MiB의 감시 한도를 설정했다. 제한은 폴링으로 감지하므로 순간 초과를 완전히 막는 OS 메모리 상한은 아니다.

일반 데스크톱 환경이며 기존 앱과 스왑이 있는 상태였다. 측정 전 가용 RAM은 약 5.4GiB, 기존 스왑 사용은 약 6.5GiB였다. 호스트 전체의 측정 중 swap-out 변화는 약 0.7MiB였다. 전용 서버의 반복 측정이나 200M 성능으로 일반화하지 않는다.

아래 `python3`은 측정에 사용한 Python 3.9.6을 뜻한다. 다른 버전이 기본이면 해당 3.9 인터프리터로 가상환경을 만든다. 저장소 루트에서 실제 LFS 원본을 준비한 뒤 실행한다. 현재 자료는 UTF-8/EUC-KR을 엄격하게 검사하며, 원본이 포인터라면 먼저 `git lfs pull`이 필요하다.

```sh
python3 -m venv .venv-bench
. .venv-bench/bin/activate
python -m pip install pandas==2.3.3 numpy==2.0.2 psutil==7.2.2
python -m unittest discover -s benches -p 'test_*.py' -v

export CARGO_BUILD_JOBS=2
cargo build --release --locked -p xazz -p xazz-runner -p xazz-exec
python benches/make_scale_data.py --source-dir examples/data --chunk-rows 100000
python benches/run_readme_benchmark.py \
  --streaming both --runs 3 \
  --timeout-seconds 120 --max-memory-mb 2048 \
  --out target/qa-166/reproduced-results.json
```

이번 맥에서는 별도 `CARGO_TARGET_DIR`을 사용했고 `--xazz-bin`으로 그 디렉터리의 `release/xazz`를 지정했다. 동일 디렉터리에 `xazz-runner`·`xazz-exec`가 있어야 한다. 별도 데이터 디렉터리는 생성기에 `--output-dir`, 측정기에 `--data-dir`을 지정한다. SDK 기본 선택이 맞지 않는 환경은 설치된 호환 SDK를 명시해야 한다.

원시 로그는 측정자의 로컬 `target/qa-166/`에 보존했고 저장소에 올리지 않았다. Python 버전별 테스트 로그, 실패 재현, 생성 로그, correctness 사례, 실측 전체 stdout/stderr 및 전체 입력 대조 결과를 포함한다. 저장소에는 재현 코드와 개별 수치·해시·환경·검증 요약 JSON을 남긴다.

## 200M 실행 판단과 남은 일

이번 원본의 xlarge 파일 예상 크기는 헤더를 한 번만 포함해 **6,505,447,832바이트(약 6.06GiB)**다. 행 수와 반복 규칙에서 계산한 크기이며 200M 파일을 실제 생성했다는 뜻은 아니다. 정규화 조각과 완성 전 임시 출력, 기존 파일을 교체할 때의 추가 디스크 공간도 필요하다.

4M 관측 RSS에 행 증가 배수 49를 단순히 곱하면 pandas 약 59GiB, Xazz off 약 33GiB다. 이는 메모리가 선형으로 늘어난다는 보장이 없는 **자원 검토용 계산**이며 실제 필요 메모리나 성능 수치가 아니다. 현재 런타임은 이름 붙은 P2 중간 결과 DataFrame을 메모리에 보관하므로 스트리밍 요청만으로 전체 파이프라인의 메모리 상한이 보장되지도 않는다. RAM 16GiB인 현재 맥에서 200M 전체 비교는 실행하지 않았다.

남은 작업은 실제 streaming 사용·fallback 여부를 노출하고 명시 요청의 실패를 처리하는 정책을 정한 뒤, 충분한 메모리 환경에서 200M 생성·pandas·Xazz on/off 측정을 수행하는 것이다. 그 결과와 재현 절차가 남아야 #166을 완료할 수 있다. 이번 변경은 CI 설정 파일을 수정하지 않으며 새 Python 테스트의 자동 CI 연결도 포함하지 않는다.
